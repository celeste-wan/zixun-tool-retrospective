项目概述

本项目是一个面向游戏行业客户拓展的公众号资讯分析工具，用来把分散的文章整理成有重点、方便回看的行业信息。它覆盖了文章收集、正文获取、相关性判断、事件分类、重复信息合并、报告撰写和网页发布。

项目定位：针对云计算/AI 厂商拓展游戏行业客户时的信息搜集需求，搭建以 WeWe RSS 为文章入口、Python 为流程控制、Claude 为分析助手、Markdown/HTML 为输出的日报工具。随着使用深入，系统又增加了健康检查、限流重试、OCR、去重、静态发布、环境变量配置和 Skill 迁移。

01

项目背景

原来的工作问题

  • 信息源多：要同时关注阿里、华为、腾讯、字节的云和 AI 动态，以及游戏媒体、游戏厂商和平台政策。
  • 需要关注重点：重点不是泛泛看新闻，而是找与游戏客户有关的合作、AI 应用、产品、融资和行业变化。
  • 人工整理重复：每天要打开多个公众号，判断文章是否相关、阅读正文、提取数据、合并重复报道，再按固定格式写报告。
  • 原始信息不完整：RSS 通常只有标题和链接，正文要逐篇打开；同一事件也可能有不同时间、说法和数据。
  • 需要长期积累：单日看完还不够，还要能按日期回看，持续了解产品和行业变化。

我重新想了一下需求

要解决的并不只是“让 AI 总结文章”，而是把每天变化、格式各异的文章，整理成一份稳定、方便使用的报告。所以我先把收集、筛选和分类规则定下来，再让 AI 处理需要理解上下文的部分。

原来的方式分别打开文章 → 凭印象判断是否相关 → 手动摘录 → 遇到重复报道再返工 → 报告格式不稳定
工具化后的方式RSS 统一收集 → 批量获取正文 → 按规则筛选 → AI 辅助归类和合并 → 固定格式输出 → 异常单独列出
02

使用场景

场景 A：每日竞品与行业扫描

每天围绕四家重点友商和游戏行业媒体生成一份固定格式的报告。先看核心内容，再看友商合作、AI 游戏与相关项目、企业动态、客户动态和行业报告，用于晨会、周会或业务跟进前快速了解情况。

场景 B：识别游戏客户的云与 AI 需求

报告不是简单摘抄新闻，而是重点看“云/AI 厂商—游戏客户—解决方案”这条关系。比如，游戏公司使用 AI 做美术、测试、广告素材或数据分析时，可以进一步判断他们可能需要哪些算力、模型、存储和开发服务。

场景 C：跟踪游戏产品与企业经营信号

把新游上线、测试、市场表现、长线运营、财报和融资分别归类。同一项目可能同时反映产品机会、技术应用和公司经营情况，因此主要看文章在讲什么，以及事件实际发生的时间，而不是只看标题。

场景 D：保留和复用历史信息

Markdown 方便继续编辑，HTML 方便浏览和分享；历史报告按日期保存，可以回看产品、平台政策、出海趋势和 AI 应用的变化。后来做迁移时，又把“只看报告”和“重新运行工具”分成两个包，避免互相影响。

应用价值：对业务工作来说，AI 提效不仅是缩短一次处理时间，也包括把已经形成的规则、结构和判断方法保留下来，方便后续继续使用。

03

系统设计

数据处理流程

01 / SOURCE

订阅采集

WeWe RSS 通过微信读书账号同步公众号更新，Docker 容器和 SQLite 数据卷保存文章元数据。

02 / FETCH

正文获取

Python 按北京时间筛选目标日期，用移动端 UA 逐篇获取微信正文，并输出结构化 JSON。

03 / ANALYZE

语义分析

Claude 根据规则和模板判断归属、提取重点、合并重复事件，并形成统一表达。

04 / PUBLISH

报告发布

Markdown 保留编辑能力，网页生成器输出 HTML 报告，便于浏览、回看和分享。

05 / REVIEW

结果复核

健康检查、失败状态、待确认清单和 OCR 结果用于标识不确定内容，人工复核关键边界。

各部分分别负责什么

  • 程序负责固定步骤：日期筛选、RSS 扫描、正文抓取、文件保存、网页生成和状态记录由程序完成，保证每次流程基本一致。
  • AI 负责理解内容：文章主体判断、重复报道合并、重点提炼、分点表达和行业意义归纳交给 Claude 辅助完成。
  • 人工负责关键判断：融资实际时间、活动预告与已发生事件的区分、榜单图片是否完整，以及报告能否对外分享，仍需结合证据确认。
  • 不同格式各有用途：JSON 用于处理过程，Markdown 用于编辑，HTML 用于阅读，Skill 用于迁移和复用这套流程。
关键设计

保留“待确认清单”。正文抓取失败、榜单图片缺失、来源重复或分类存疑时，不强行下结论，而是保留问题和原文，方便后续人工核对。

05

问题与改进

01

RSS 抓取不全，微信读书账号会掉线

表现：有些订阅号长时间没有更新，健康检查还曾发现微信读书账号失效。
处理：增加健康检查；整理前先刷新一次；当天没有文章的订阅号按间隔重试；账号失效时暂停流程，提醒重新扫码，不继续生成可能不完整的报告。
经验：自动化首先要知道什么时候没有拿到数据，不能把空结果当成“当天没有变化”。

02

RSS 只有标题和链接，正文还要单独获取

表现：正文需要逐篇请求，部分文章会返回空内容、限制页或错误页。
处理：单独编写正文抓取脚本；使用移动端 UA；记录每篇文章的成功或失败状态；用 JSON 保存标题、来源、时间、链接、正文和错误原因；失败文章进入待确认清单。
经验：单篇文章失败不应该影响整份日报，抓取和整理需要分开处理。

03

同一事件经常被多家媒体重复报道

表现：《凡应》《湮灭之潮》《剑网3》《诡秘之主》等事件在同一天有多篇报道。
处理：从按文章整理改为按事件整理；选择信息较完整的报道作为主条目，补充其他报道中的新增事实，保留所有原文链接，重复稿放入待确认清单。
经验：报告应该帮助人理解发生了什么，而不是简单增加文章数量。

04

榜单和周预告的重要数据在图片里

表现：排行榜完整数据和 GameRes 总览表通常不在正文文本中。
处理：加入 OCR；GameRes 只整理规则要求的删档测试；没有图片时不猜测数据，并在报告中说明哪些内容没有核验。
经验：材料不完整时要明确说明，而不是为了让报告看起来完整而补写内容。

05

网页表格排版不够美观

表现：长标题链接不能换行，挤占了其他列的宽度，正文出现逐字竖排。
处理：检查 CSS 后发现链接列设置了 `white-space: nowrap`；改为固定列宽、允许链接换行，并重新生成页面检查效果。
经验：文件生成成功不代表页面使用体验良好，还需要检查实际打开后的效果。

06

一开始只能在当前电脑运行

表现：一些脚本使用了当前电脑的固定路径和授权配置，报告、运行数据和临时文件也放在同一个项目目录中。
处理：增加统一 `config.py`；项目路径改为从脚本位置读取，也支持环境变量；WeWe 授权码改为环境变量或 Keychain；网页服务默认只在本机运行；补充依赖清单、`.env.example`、`.gitignore`、静态导出和迁移 Skill。
经验：项目真正被使用一段时间后，才会发现可维护和可迁移方面的问题，这些问题需要在后续迭代中补齐。

06

项目成效与边界

阶段性成果

  • 从文章收集到 HTML 报告的流程已经跑通，日常整理不再需要从头设计格式和栏目。
  • 规则从最初的竞品和行业分类，逐步细化到字段、事件类型、时间判断、重复报道处理、OCR 和待确认内容。
  • 截至 8 月底，项目已经保存 51 份 HTML 历史报告，可以按日期回看。
  • 历史补整理阶段处理了 12 天、425 篇文章；其中 25 篇未能成功获取正文，已保留在待确认清单。
  • 工具目前可以分别作为静态报告、完整源码和 Claude Skill 进行迁移。

几个重要选择

选择原因
先定规则，再让 AI 总结保证日报格式基本一致，也减少 AI 每天改变重点和结构的情况。
不确定内容也保留抓取失败、分类存疑和重复报道放到待确认清单，方便后续人工核对。
保留人工复核账号授权、事件实际时间、图片内容和对外分享范围，不能完全交给自动流程。
先在本地验证先把工作流程跑通，再决定是否上云，避免一开始就增加部署和权限管理成本。

当前边界

  • 尚未建立严格的人工时间基线、阅读时长对比、错误率趋势或业务转化指标，因此不能直接宣称“节省了多少工时”或“带来了多少客户”。
  • WeWe RSS 和微信读书授权仍是外部依赖，账号掉线和接口限流无法由工具完全消除。
  • 公众号正文、运行 JSON 和缓存文件涉及版权、隐私和第三方 API 处理边界，分发时必须与静态报告隔离。
  • Skill 可以迁移规则和操作知识，但不会自动提供 Docker、WeWe 数据库、微信读书授权或 API Key。

面试准备

90 秒项目介绍

项目介绍：我做了一套公众号资讯整理工具，主要服务于云计算/AI 厂商拓展游戏行业客户的工作。原来的流程是分别打开多个公众号，逐篇判断、摘录和整理，既耗时，也容易漏掉信息或重复整理。现在由 WeWe RSS 负责收集文章，Python 负责按日期获取正文和记录状态，Claude 辅助分类、合并重复报道和撰写摘要，最后输出 Markdown 和 HTML 报告。项目从竞争对手模板开始，后来扩展到行业四个模块，并逐步处理了账号掉线、接口限流、图片榜单、网页排版和跨设备迁移等问题。阶段性结果是 12 天抓取 425 篇文章，成功获取 400 篇正文，并保存了 51 份历史 HTML 报告。下一步会补充人工时间和准确率等指标，再评估是否需要多人共享。

为什么没有让 AI 直接读取 RSS 并输出报告？

回答主线：文章收集、日期筛选、失败重试和文件输出都有明确规则，交给程序更稳定；判断文章是否相关、合并重复报道和提炼重点，需要理解上下文，适合让 Claude 辅助完成。这样出了问题也比较容易判断，是文章没有抓到，还是分析结果需要调整。

实际做法是：WeWe RSS 负责收集，Python 负责抓取和记录状态，Claude 负责分类和撰写，Markdown/HTML 负责输出。

你遇到过最典型的问题是什么？

回答主线：最典型的问题是 RSS 和微信读书账号不稳定。健康检查曾发现账号失效，自动任务因此在发布前停止；账号恢复后，接口仍会限流，部分订阅号也可能暂时没有返回当天文章。

我增加了健康检查和全量刷新，对缺少当天文章的来源按时间间隔重试；每篇正文单独记录成功或失败，无法确认的内容放进待确认清单。这个过程让我认识到，自动化流程需要同时设计正常流程和异常处理。

这个工具的 AI 提效体现在哪里？

回答主线：AI 主要帮我完成三类工作：判断文章是否和业务有关，把多篇报道合并成一个事件，以及把不同文章整理成统一格式。我的工作从逐篇摘录，转向制定规则、检查事实、处理特殊情况和使用报告结论。

AI 不直接作为事实来源。正文需要先获取，关键数据保留原文链接，无法确认的内容保留待确认状态。

如果重新建设，你会优先改进什么？

回答主线：第一，尽早记录人工处理时间和准确率，清楚比较工具带来的变化；第二，一开始就统一配置并固定依赖版本，减少后期迁移时的返工；第三，为每个事件建立固定编号和来源记录，方便持续跟踪同一产品或公司。

高频追问关键词

  • 需求定义：信息过载、客户拓展、竞品与行业双重视角
  • 架构：RSS / Docker / SQLite / Python / Claude / Markdown / HTML
  • 可靠性：健康检查、限流重试、失败隔离、待确认清单
  • 质量：规则、模板、去重、事件实际发生时间、OCR

  • 边界：版权、凭据、账号授权、没有夸大的 ROI 指标

后续规划

P0：先把安全和运行稳定性做好

  • 更换曾经出现在旧日志和旧配置中的 WeWe 授权码。
  • 把项目放入 Git，保留规则、配置和模板的修改记录。
  • 固定 Python 和依赖版本，补充日期判断、授权码缺失、正文为空、重复链接和静态导出等测试。

P1：记录实际的效率变化

  • 记录人工整理需要多长时间，包括阅读、写初稿和修改的时间。
  • 记录正文获取成功率、文章覆盖情况、重复报道合并情况和人工修改量。
  • 定期抽查分类结果，确认报告质量是否稳定。

P2：支持按公司和产品长期回看

  • 为公司、游戏、模型和事件建立统一记录。
  • 给同一事件固定编号，支持跨日期合并和查看发展过程。
  • 增加客户机会字段，记录可能的需求、技术切入点、后续建议和证据链接。

P3：评估多人共享

  • 继续使用静态报告作为简单的分享方式。
  • 如果确实需要多人实时检查更新，再考虑部署带登录和权限控制的远程服务。
  • Skill 可以迁移操作方法，但每台电脑仍需单独配置 RSS、微信读书账号、数据库和 API Key。

这个项目值得重点介绍的，不只是调用了一个大模型，而是从实际工作出发，逐步补充规则、状态记录、异常处理、质量检查和迁移能力。它体现了我对业务问题的理解，以及把 AI 工具真正用于日常工作的过程。
